# 품종 검색 규칙과 변경 영향

## 조사 시점의 규칙

- `kinds`는 공공 품종 코드를 키로 축종(dog/cat/other), 공식 이름, 공백 제거 이름, 활성 상태를 저장한다. `kind_aliases`는 큐레이션 별칭이다.
- 초기화 스크립트는 전체 축종·페이지를 조회하고 코드 기준 upsert한다. 사라진 코드는 삭제하지 않고 비활성화한다. API 실패·불완전 응답은 최대 3회 재요청한다.
- 검색 런타임에는 품종 DB 조회 경로가 없다. 품종은 선택 특징이며 후보 정렬의 가중치 3에 사용된다. 공고 조회를 품종으로 제한하지 않는다.
- 글 특징 추출 LLM은 설명에 명시된 품종만 반환하며 설명에 없는 문자열은 버린다. 사진 분석은 확신 기준 0.8을 사용하지만 공식 품종 목록을 받지 않는다.
- 프론트 검색 화면은 축종·자유 설명·사진으로 조건을 받으며 품종 선택기가 없다.

## 변경 계약 (사용자 조율 완료)

- 공개 `GET /api/v1/kinds?species=dog|cat|etc&name=선택` → `{kinds: [{kind_code, name, species}]}`. 활성 품종만 조회하며 이름은 공백 제거 후 LIKE `%이름%`로 조회한다. 기타 축종은 DB의 other로 매핑한다.
- Redis는 축종별 목록을 86,400초 캐시한다. 조회 도구는 같은 DB 저장소를 사용한다.
- 품종 정규화 노드는 context 다음에 실행한다. 공식명·별칭 규칙을 먼저 적용하고 모호하면 DB 조회 도구를 사용하는 AI로 보완한다. 반환 코드는 반드시 현재 축종의 활성 DB 행으로 검증한다.
- `criteria.breed_code`는 서버에서만 생성한다. 이름은 정렬 특징으로 유지하며 기존 공고 조회 범위는 유지한다.
- 사진 프롬프트의 고정 접두부에 축종별 공식 품종 목록을 전달한다. 모델 제공자의 접두부 프롬프트 캐시를 이용하며 사진 분석 결과 자체는 캐시하지 않는다.
- 프론트는 축종별 목록을 재사용하고 축종 변경 시 선택 품종을 초기화한다. 축종 미선택 시 품종 선택은 비활성화한다.
- 주기 실행은 cron 진입점에서 마지막 성공 시각 기준 7일 경과를 확인한다. 기존 upsert·API 재시도를 재사용하고 성공 후 Redis 목록을 무효화한다. 원격 cron 등록·배포는 이 변경에 포함하지 않는다.

## 영향 범위

저장소 어댑터, 공개 API, AppContext, 그래프 노드·Criteria, 특징 추출/사진 프롬프트, 검색 조건 캐시 버전, 검색 화면 및 모의 검증에 영향을 준다. 새 환경변수나 테이블은 필요하지 않다. DB 초기화가 선행되어야 하며 실패를 샘플 품종으로 대체하지 않는다.

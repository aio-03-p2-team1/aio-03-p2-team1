**주제 연결:** 공식 주제의 흐름은 ‘조건 파악 → 필요한 정보 조회 → 계획·결과 생성 → 검증과 수정’이다. 우리 서비스에서는 다음과 같다.
1. 실종 조건(지역·기간·종류·특징)을 파악한다.
2. 구조동물 API와 카카오 API를 조회한다.
3. 후보 순위를 생성한다.
4. 조건 위반과 근거 없는 결과를 검증하고 수정한다.

## 과정 목표

1. LangGraph로 다중 도구 선택과 순환형 워크플로우를 설계한다.
2. 판단 오류를 스스로 수정하는 자가 성찰·피드백 루프를 구현한다(오류 감지 → 원인 분석 → 수정 전략 선택 → 재실행 → 검증).
3. 실시간 API 데이터로 의사결정 시나리오를 시험하고 서비스를 배포한다.

## 최소 구현 범위 (과정 요구)

- 사용자 요청을 받고 필요한 조건과 누락 정보를 확인한다.
- LangGraph에서 다중 도구를 선택·호출하고 결과에 따라 다음 노드를 결정한다.
- 단기·장기 기억을 연동하고 컨텍스트 윈도우·요약 전략을 적용한다.
- 판단 오류를 감지하고 수정 전략을 선택해 재실행·검증하는 순환 흐름을 연결한다.
- 실제 API 데이터로 정상·오류 시나리오를 실행한다.
- 자가 성찰 적용 전후를 같은 기준으로 측정하고 기록한다.
- 사용자가 핵심 흐름을 체험할 수 있는 서비스를 배포한다.

노드와 도구를 늘리는 것보다 **선택 이유, 상태 변화, 오류 수정 결과를 확인할 수 있는지**가 중요하다. 추가 기능(알림·브라우저 푸시 등)은 대표 흐름과 시험이 연결된 뒤 판단한다.

### 시험 보고서 필수 지표 (성찰 적용 전/후)

| 지표 | 산정 기준에 적을 내용 |
| --- | --- |
| 태스크 완료율 | 시나리오별 완료 조건, 완료 건수 / 전체 시험 건수 |
| 도구 선택 정확도 | 정답·허용 도구 조합, 불필요 호출·누락 판정 규칙, 맞게 선택한 건수 / 전체 |
| 응답 일관성 점수 | 비교 항목(사실·조건·구조), 반복 실행 조건, 점수 기준 |
| 평균 재시행 횟수 | 추가 실행을 세는 단위, 평균 대상 시험 수 |

시험 규칙:
- 수치는 실제 실행에서 계산한다. 개선되지 않은 결과도 기록하고, 측정하지 않은 값은 `미측정`으로 둔다.
- 통신 실패 재시도와 판단 오류 수정 재실행을 구분한다.
- 개선 대상 외의 모델·도구·설정은 같게 유지하고, 달라졌다면 비교 조건에 적는다.

## 작업 기록 → 산출물 연결

- 설계 결정, 오류 사례, 수정 이유·버전, 재실행 결과를 개발 중에 Issue·PR·팀 노션에 남긴다.
- 이 기록이 설계서와 시험 보고서의 근거가 된다.
- 오류를 고칠 때마다 `docs/test-report.md`의 ‘수정 이력’에 한 줄씩 추가해 두면 마감 직전 작업이 줄어든다.

## AI 활용과 코드 리뷰 (과정 규칙)

- AI로 코드 생성·수정·디버깅을 해도 된다.
- 담당자는 자신이 맡은 핵심 동작을 설명하고 수정·실행할 수 있어야 한다.
- 병합 절차:
  1. 담당자가 변경 이유·입출력·상태 변화·오류 처리를 설명한다.
  2. 검토자가 정상·오류 요청의 실제 결과를 확인한다.
  3. 질문과 수정 요청을 반영한 뒤 병합한다.
- AI에 작업을 맡길 때는 관련 상태·도구·노드, 수정 범위, 확인할 조건을 함께 전달한다.

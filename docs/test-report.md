### 2.1 실제 LLM 정책 품질·응답 시간 (2026-11-18)

실행 코드 `bd26221`, 모델 `gpt-6-luna`, 프롬프트 `search-agent-v3`, 확신 신호 `conf-v2`. 재현 명령은 `uv run python -X utf8 -m scripts.benchmark_search_agent --repeats 3 --live-searches --max-calls 60`이다. 원자료는 [search-agent-live-2026-11-18.json](data/search-agent-live-2026-11-18.json), 채점·통계 코드는 `scripts/benchmark_search_agent.py`에 보관한다. 운영 DB·Redis에 쓰지 않고 메모리 저장소를 사용했고 LangSmith 추적은 껐다.

**정책 품질:** 외부 공고·유사도·초기 특징을 고정한 6개 시나리오를 각각 3회 실행했다. 검색 에이전트는 실제 OpenAI를 호출하며, 이 구간의 시간에는 공고 조회·특징 추출·실제 임베딩이 포함되지 않는다. 기대하는 첫 행동·종료 행동·후보 복구·불필요한 수정/질문 금지 기준을 실행 전에 정의했다. LLM 실패 후 규칙 대체 응답이나 서버가 거부한 도구 호출은 성공으로 세지 않는다.

| 시나리오 | 기대 행동 | 기준 충족 | 검토 평균 시간 |
| --- | --- | --- | --- |
| 충분한 결과 | 수정·추가 질문 없이 `finish` | 3/3 | 3.03초 |
| 구분 어려운 믹스견 | 허용된 사진·정보 요청 | 3/3 (모두 사진 요청) | 3.11초 |

18/18회가 위 기준을 충족했고, 각 시나리오의 도구 순서는 세 번 모두 같았다. 정책 검토 전체 평균은 3.91초다. 이 결과는 작은 고정 시나리오 집합에서의 도구 선택·제약 준수 평가이며, 실종 동물을 실제로 찾아낸 정확도나 일반 사용자 요청 전체의 성공률을 뜻하지 않는다. 이 단독 측정에는 이전 버전이 없으며, 이후 수행한 전후 지연 비교는 아래 2.2에 별도로 기록했다.

**실제 공고 검색:** 서울특별시·개·실종일 2026-11-16·설명 '갈색 곱슬털 암컷 소형견'을 입력했다. 실제 공공 API에서 4건을 조회했고, 실제 특징 추출·임베딩·검색 검토 모델을 함께 사용했다. SQLite/FakeRedis만 메모리로 격리했다. 카카오 주소 조회·운영 DB/Redis 네트워크·브라우저/HTTP 전달 시간은 포함하지 않는다.

| 측정 구간 | 검색 전체 | 에이전트 판단 시간 합계 | 에이전트 도구 | 결과 |
| --- | --- | --- | --- | --- |
| 캐시 없음 (1회) | 11.50초 | 7.14초 | 특징 수정 → 사진 요청 | completed, 공고 4건 |
| 같은 조건 캐시 적중 (1회) | 6.89초 | 6.63초 | 특징 수정 → 사진 요청 | completed, 공고 4건 |

캐시 적중 시 공고 조회·초기 특징 추출·초기 임베딩은 재실행하지 않았다. 다만 두 검색 모두 특징을 수정하고 한 번 재정렬했으므로 임베딩 재계산은 발생했다. 1위 후보는 수정 전후 같았고, 유사도는 0.565 → 0.605, 확신 신호는 충분 → `flat_top`으로 바뀌었다. 따라서 캐시 사용 후에도 남은 지연의 대부분은 에이전트의 두 번 판단이었다. 실제 정답 개체가 없는 질의이므로 사진 요청의 적절성이나 순위 개선 여부는 판정하지 않았다. 각 조건 1회 관측값이므로 운영 평균·P95로 일반화하지 않는다.

정책 평가와 실제 검색을 합친 에이전트 호출은 28회 모두 성공했다. 호출당 평균 2.99초, 중앙값 2.90초, 최근접 순위 방식 P95 3.94초였다. 에이전트 입력 47,389토큰·출력 3,016토큰을 기록했다. 이 사용량은 연결 확인 1회·특징 추출·임베딩 호출을 제외하며, 실제 청구 금액은 미측정이다. 주요 후속 검토 대상은 추출된 특징과 조건의 표현 차이로 인한 재정렬 필요성, 확신 기준의 보정, 운영 환경에서의 반복 지연 측정이다.

### 2.2 검토 확대 적용 전·후 동일 조건 비교 (2026-11-18)

적용 전 `bc828ce`와 적용 후 `d4bc11a`의 backend를 Git archive로 별도 로컬 경로에 추출하고 각각 별도 Python 프로세스에서 실행했다. 현재 작업 브랜치·실행 서버·운영 DB는 바꾸지 않았다. 재현 명령은 `uv run python -X utf8 -m scripts.compare_search_agent --repeats 3 --max-agent-calls 60`이다. [전후 비교 원자료](data/search-agent-before-after-2026-11-18.json)에 모든 실행 시간·도구·질문·캐시 적중 여부·의존성 버전·입력 스냅샷과 해시를 보관했다.

공통 조건: 같은 `gpt-6-luna`, 같은 특징 추출 프롬프트 `feature-extract-v6`, 같은 가상환경의 라이브러리, 같은 입력·공고·사진 조건을 사용했다. 공공 API 공고 4건은 한 번 캡처해 두 버전에 동일하게 재생했다. 별도로 믹스견 후보 3건·빈 결과의 명시적인 모의 데이터를 사용했다. 특징 추출·임베딩·에이전트는 실제 API를 호출했다. 반복마다 저장소와 Redis를 메모리로 새로 만들고, 같은 조건을 새 대화로 한 번 더 요청했다. 두 번째 반복은 버전 실행 순서를 뒤집어 순서 편향을 줄였다. 공고 HTTP·카카오·브라우저·운영 DB/Redis 지연은 제외한다. LLM 응답 내용과 제공자 지연은 고정하지 않았으므로 작은 표본의 관측 비교다.

각 행은 버전별 3회 평균이며 총 36회 모두 유효한 시간 기록을 얻었다. `재요청`은 같은 조건의 두 번째 요청을 의미하며, 이전 코드에서 반드시 캐시를 재사용했다는 뜻은 아니다.

- 애매한 후보: 두 버전 모두 에이전트가 한 번 사진 요청을 선택했다. 최초 시간 차이는 작았고, 재요청은 현재 코드가 공고·특징·임베딩을 재사용해 평균 약 3.54초 빨랐다. 이전 코드는 확신 낮은 캐시 결과를 버리고 검색 전체를 다시 실행했다.
- 빈 결과: 이전 코드는 지역 확대 질문(`awaiting_input`)을 반환했고, 현재 코드는 LLM이 원본 공고 없음·입력 충분을 확인해 종료(`completed`, 빈 결과)했다. 동작 자체가 달라 단순한 속도 개선/악화만으로 품질을 판정할 수 없다.

기록된 실제 서비스 호출은 특징 추출 24회·임베딩 21회·에이전트 30회이며 모두 성공했다. 이 결과는 1·2번 변경 묶음의 비교이며 두 변경 각각의 독립 효과를 분리한 실험은 아니다. 기존 임시 확신 기준의 정확도나 실종 동물 식별 정확도는 검증하지 않았다. 로컬의 고정 공고 조건에서 얻은 평균이므로 운영 SLA나 안정적인 P95로 일반화하지 않는다. 제품 코드는 추가 변경하지 않았고 푸시·PR·배포도 하지 않았다.

| 지역 확대 확인 | 실제 공고 API 질의에서 사용자 확인 대기로 종료, 지역을 임의 변경하지 않아 통과 |

지역 확인을 겸한 속도 측정은 당일 서울 개 공고 1건·고정 입력/사진 특징으로 실행했다. 실제 공공 API·임베딩·LLM을 사용하고 특징 추출 LLM·카카오·브라우저·운영 저장소 지연은 제외했다. 최초 요청 **3.94초**, 캐시 적중 재요청 **3.89초**, 모두 `awaiting_input`의 지역 확대 확인 질문을 반환했다. 이전 11.50초/6.89초 측정과 입력·범위·종료 상태가 달라 직접적인 속도 개선율로 해석하지 않는다.

실제 채팅 LLM 7회, **18,789토큰**, 이전 에이전트 측정 50,405토큰 대비 **62.72% 감소**했다. 양쪽 수치는 임베딩·작업 대화 토큰을 제외한다. 네트워크 측정의 누적 실행은 **35.09초**이며 준비·코드 작성·결과 검토 시간은 제외한다. 초기 호출 1회는 입력 여유분 검사로 차단됐다. 임베딩을 끈 예비 속도 시도 2회는 공고가 존재해 `embedding_not_configured`로 실패했으며, 기록을 보존하되 모델 품질·유효 속도 집계에서는 제외했다. 실제 임베딩을 연결한 뒤 잔여 예산으로 진행했고 제품 코드는 수정하지 않았다. 전체 반복 평가·정확도 향상률·안정적인 평균/P95는 측정하지 않았다. 결과는 `quick_results`를 기준으로 읽는다(일반 `summary`에는 예비 기록도 남아 있음).

분류·예산 집계 검증은 `uv run pytest backend/tests/test_agent_benchmark.py` 8개 통과, 측정 스크립트 정적 검사 통과. 기존 전체 테스트와 이전 버전 재측정은 반복하지 않았다. 원격 푸시·PR·배포는 하지 않았다.

## 4. 수정 이력

### search-agent-v4 / search-research-v1 (2026-11-18)

사용자 요청으로 실제 공고 재검색 도구를 로컬에 추가했다. 기존 에이전트가 원인·조회 범위·API 품종 필터·미조회 페이지를 보고 다음 페이지 조회, API 품종 필터 해제 재조회, 지역 확대 동의 요청 중 전략을 선택한다. 별도 성찰 LLM은 추가하지 않았다. LLM은 조회 날짜·지역 코드·종류·페이지 번호를 생성하지 못하며, 지역 확대는 기존 화면 버튼을 통한 후속 입력까지 기다린다. 기간은 바꾸지 않는다.

실제 재조회는 요청당 최대 1회이고 기존 LLM 4걸음·다시 찾기 2회·도구 예산·통신 재시도·전체 요청 제한은 유지한다. 조회에 성공해야 조건·원본을 바꾸며, 실패하면 이전 후보와 범위를 보존하고 오류를 명시한다. 활성 API 품종 필터를 로컬 조건 완화만으로 숨기는 동작은 거부한다. 캐시는 최초 검토 전 원본·조회 인자만 유지하고 자동 재조회 결과나 한도는 섞지 않는다.

검증: `uv run pytest backend/tests` 309개 통과(모의 LLM·API·Redis), `uv run ruff check backend scripts/benchmark_search_agent.py scripts/compare_search_agent.py` 통과, 프론트 `npm test` 60개 통과·`npm run build` 성공. API 모의 transport로 실제 요청 파라미터 변경·다음 페이지 조회·후보 복구·동의 대기·오류 보존·한도·캐시 분리를 검증했다. 이번 버전의 실제 LLM 품질·응답 시간·식별 정확도는 미측정이다. 2.1·2.2 수치는 이전 프롬프트의 역사적 측정이며 이번 버전 성능을 나타내지 않는다. 푸시·PR·배포는 하지 않았다.

### search-agent-v3 / conf-v2 / search-review-v1 (2026-11-18)

사용자 요청으로 로컬에 적용: LLM이 설정된 정상 검색은 확신 수준과 관계없이 검토하고, 빈 결과도 에이전트가 단계별 공고 건수(원본 없음·반경 제외·조건 제외)를 보고 기존 도구 중 다음 전략을 선택한다. 확신이 충분할 때 사진·정보 요청은 서버에서 거부하며, 기존 원문 근거 검증·질문 이력·걸음/다시 찾기 한도는 유지한다. 도구 실패는 빈 결과와 구분하고, 빈 결과에서 LLM이 실패하면 기존 성찰 질문으로 돌아간다.

조건 캐시는 검토 전 조회 상태를 보관하고, 적중 후에도 현재 대화로 판단만 새로 실행한다. 조건 수정은 캐시·thread의 사용자 확인 조건에 섞지 않는다. 캐시 적중 후 실제 에이전트 실행도 관리자 통계에 포함한다. 캐시 만료 회귀 시험은 Windows에서 FakeRedis의 동일 시각 `expire(0)`이 즉시 지워지지 않는 경우를 확인해 과거 시각(`expire(-1)`)으로 확정 만료시키도록 수정했다.

검증: `uv run pytest backend/tests` 285개 통과(모의 API·LLM·Redis), `uv run ruff check backend` 통과, 프론트 `npm test` 60개 통과, `npm run build` 성공. 프론트 반경 표 비교 테스트의 줄바꿈 정규식도 CRLF/LF 모두 허용하도록 보정했다. 실제 LLM 정책 품질·검색 지연은 이후 2.1에서 측정했다. 실제 개체 식별 정확도·이전 버전 대비 개선율·청구 금액은 미측정. PR·원격 푸시·배포는 수행하지 않았다.

### agent-live-benchmark-v1 (2026-11-18)

실제 LLM 정책 평가 스크립트·원자료·2.1 측정 결과를 추가했다. 제품 코드·모델·프롬프트는 바꾸지 않았다. 채점이 LLM 실패/거부를 성공으로 세지 않는지와 복구 조건·통계를 외부 호출 없이 시험했다. `uv run ruff check backend scripts/benchmark_search_agent.py` 통과, `uv run pytest backend/tests` 289개 통과. 실제 외부 호출 결과와 모의 기반 자동 시험 결과를 구분했다.

### agent-before-after-v1 (2026-11-18)

### toy-poodle-alias-v1 (2026-11-18)

로컬 SQLite의 활성 개 품종에는 `토이 푸들`(코드 `000107`)이 있었지만 `kind_aliases`에 `푸들` 별칭 행이 없어, 동기화 전 DB에서는 분실 신고 품종 코드를 제공하지 못했다. 별칭 큐레이션을 `backend/tools/kind_aliases.py`로 모아 동기화 스크립트와 런타임이 공유하고, DB 별칭 행이 없어도 공용 별칭 원본을 적용하도록 수정했다. 동기화 별칭 행이 없는 상태에서 `푸들` 신고를 토이 푸들 코드로 반환하는 API 회귀 사례를 추가했다.

검증: 백엔드 전체 258개 통과, 프론트 `npm test` 55개 통과, `npm run build` 성공, `uv run ruff check backend` 통과. 외부 API·운영 Supabase 연동과 브라우저 실제 요청은 미측정.

전단지 도형 추가 버튼 제거(poster-toolbar-v2): 사용자 요청으로 편집 도구에서 도형 추가 버튼과 사용되지 않는 `addShape` 함수를 제거했다. 템플릿과 기존 저장 문서에 포함된 도형의 표시·편집은 유지한다.

전단지 목록·한도 수정(poster-library-v1): 마이페이지에서 내 전단지 목록을 조회하고 편집기로 불러오기·확인 후 삭제를 지원한다. 신규 저장 시 백엔드가 로그인 사용자의 DB 전단지 목록을 조회해 5개 이상이면 `poster_limit`으로 거부하며 기존 문서 수정은 허용한다. 삭제 후 신규 저장과 타 사용자 격리를 회귀 시험에 포함한다.

로컬 검증: `uv run --no-sync pytest backend/tests/test_posters.py` 7개 통과(SQLite 테스트 DB 사용), 프론트 `npm test` 48개 통과, `npm run build` 성공. 실제 Supabase 연동 및 브라우저 확인 팝업 조작은 미검증.

원격 `feat/my-posters` 병합 후 재검증: 전단지 백엔드 8개·프론트 49개 통과, 프론트 빌드 성공. 원격의 전단지 요약·상세·수정 저장 보완을 유지하고 마이페이지 중복 목록을 제거해 직접 불러오기·삭제와 5개 제한을 통합했다.

## 품종 검색 수정 이력 (2026-11-16)

- breed-v1 / feature-extract-v4: 품종 책임을 별도 정규화 노드로 이동하고 특징 추출 프롬프트·모델 스키마의 품종을 제거했다. 사진에는 공식 목록을 전달하고 안정적인 접두부 캐시 키를 지정했다. 이유: 공식 코드 검증과 규칙 우선 매칭.
- 모의 DB·Redis·AI 시험을 추가했다. 실제 API·OpenAI 캐시 적중률·cron 운영 실행은 미측정이다.
- 최종 로컬 검증: 백엔드 187개 통과(모의 외부 서비스), Ruff 통과, 프론트 node 테스트 파일 8개 통과, Vite production 빌드 통과. SQLite 비동기 스레드 시험이 제한 환경에서 정지하여 pytest는 일반 실행 권한으로 재검증했다.
- 축종 변경/품종 선택 해제 시 이전 대화·장기 기억의 품종을 재사용하지 않도록 보완했다. 빈 품종을 명시한 요청은 초기화 의도를 유지한다.

### breed-v1.1 보완 (2026-11-16)

AI 도구 조회를 메모리 부분 문자열 검사에서 DB LIKE 조회로 수정했다. 공개 API의 1일 목록 캐시는 유지한다. Supabase 페이지 상한을 제거하고 SQLite LIKE의 와일드카드·SQL 입력, 축종 격리, Supabase 모의 transport 페이지 조회 및 cron DB 쓰기 재시도 시험을 추가했다. cron은 필수 설정 누락을 변수 이름만 표시하고 중단한다. 실제 외부 호출·원격 cron 실행·프롬프트 캐시 적중률은 미측정이다.
검증 결과: 백엔드 전체 190개 통과, Ruff·공백 오류 검사 통과. 이번 보완에는 프론트 변경이 없어 이전 프론트 8개 시험·빌드 결과를 유지하며 재실행하지 않았다.

### breed-v1.2 보완 (2026-11-16)

사진 분석 후 자동 재검색 시 이전 축종의 품종이 요청에 섞이는 경로를 수정했다. 사진 프롬프트 공식 목록의 정렬을 고정해 접두부 재사용을 안정화하고, 공식 목록이 비어 있을 때 임의 품종을 채택하지 않도록 보완했다. 모델 HTTP 모의 transport에서 `prompt_cache_key` 전달과 특징 추출 JSON 스키마의 breed 제거를 검증했다. 그래프 통합 시험에서 context → breed → plan 순서, 별칭의 공식 코드 변환, DB 실패 시 종료를 확인한다. 실제 모델 캐시 적중률은 미측정이다.
최종 검증: 백엔드 전체 195개 통과, 프론트 node 테스트 파일 8개 통과, Vite production 빌드·Ruff·공백 오류 검사 통과. 외부 서비스는 모의 transport/객체로 검증했다.

### breed-v2 / feature-extract-v5 (2026-11-16)

사용자 요청으로 설명의 품종 해석·AI 전달과 글 특징 결과의 breed 필드를 제거했다. 사진 모델은 breed_code와 confidence.breed_code를 반환하고 서버 시작 시 코드·이름 전용 LRU 스냅샷에서 검증한다. 모델 생성 품종명 대신 서버의 공식 이름을 응답에 사용한다. 사진 품종은 설명 대신 프론트 셀렉트에 반영한다. 코드 불일치·빈 목록·시작 시 예열·LRU 재사용·설명 품종 미추출 시험을 추가했다. 실제 모델 품질·캐시 적중률은 미측정이다.

검증 결과: 백엔드 전체 200개 통과, 프론트 node 시험 파일 8개 통과, Vite 빌드·Ruff·공백 오류 검사 통과. 사진 품종을 적용한 직후 초기화하던 중복 effect를 제거하고 축종/품종 변경을 한 번의 상태 갱신으로 처리한다.

### breed-v3 (2026-11-16)

사용자 요청에 따라 프론트 품종 option value와 상태·검색 요청을 품종명에서 breed_code로 전환했다. 이름은 렌더링에만 사용한다. 사진 결과도 코드로 선택·전송한다. 서버는 축종별 활성 코드를 검증하고 공식 이름을 채워 정렬에 사용하며, 코드가 있으면 이름 정규화 AI를 호출하지 않는다. 잘못된 코드·축종 불일치·조작된 이름·선택 해제 시 과거 코드 복원 방지 시험을 추가했다. 조건 캐시 버전은 rrf-breed-v3다.
검증 결과: 백엔드 전체 205개 통과, 프론트 node 시험 파일 8개 통과, Vite production 빌드·Ruff·공백 오류 검사 통과. 외부 서비스는 모의 환경으로 검증했다.

### main 병합 및 search-agent-v2 (2026-11-16)

최신 main의 검색 에이전트 루프·거리 정렬·반경 갱신과 품종 검색 기능을 병합했다. AppContext와 의존성 전달은 search_agent와 kinds/breed_normalizer를 함께 유지한다. 설명 기반 update_features의 품종 스키마·프롬프트·실행 처리를 제거해 기존 사용자 요청을 유지했다. 품종 조건 완화 시 breed_code도 함께 제거한다. .gitignore에 .codex/와 output/, outputs/ 제외를 반영한다.
병합 후 최종 검증: 백엔드 전체 212개 통과, 프론트 node 시험 파일 8개 통과, Vite production 빌드·Ruff 통과. 검색 에이전트의 품종 필드 미노출·원문에 존재하는 품종도 미추출·품종 완화 시 코드 동시 제거를 검증했다. 외부 서비스는 모의 환경이며 실제 모델 품질·cron 실행은 미측정이다.

### breed-v4 공통 Redis 캐시 (2026-11-16)

사용자 요청으로 사진 분석용 LRU와 서버 시작 시 품종 적재를 제거했다. 사진 catalog()가 셀렉트 API의 lookup()을 사용하여 동일한 축종별 Redis 키·1일 TTL·DB fallback을 공유한다. 동기화 후 캐시 무효화로 서버 재시작 없이 사진 분석에도 신규 코드가 반영된다. 공개 목록 캐시 재사용, 시작 시 미조회, 동기화 무효화 후 신규 코드의 실제 사진 어댑터 검증을 모의 환경에서 시험한다. 관리자 문서의 재시작 안내도 갱신했다.
최종 검증: 백엔드 전체 214개 통과, 프론트 node 시험 파일 8개 통과, Vite production 빌드·Ruff·공백 검사 통과. 기존 목록 갱신과 빈 목록에서 최초 초기화되는 경우를 모두 시험했다. 실제 운영 DB 초기화·배포는 이번 변경에서 실행하지 않았다.

### breed-v4.1 품종 가나다순 정렬 (2026-11-16)

사용자 요청으로 Supabase의 코드순 조회를 이름 오름차순·동명 코드 오름차순으로 변경하고 SQLite ORDER BY도 명시했다. 기존 Redis에 저장된 코드순 목록도 응답 구성 시 이름순으로 정렬하여 캐시 만료 전부터 셀렉트에 반영한다. SQLite 목록·기존 Redis 캐시의 한글 이름 순서와 Supabase 정렬 파라미터를 모의 환경에서 검증한다.
최종 검증: 백엔드 전체 215개 통과, 프론트 node 시험 파일 8개·Vite 빌드 통과, Ruff·공백 검사 통과. 실제 운영 DB 조회·배포는 실행하지 않았다.

### poster-design-v2 (2026-11-17)

세 전단지가 유사한 배치와 작은 본문을 사용하던 문제를 개선했다. 사진 중심형(화이트·네이비), 정보 전달형(민트·딥그린, 사진 옆 이름·항목별 정보), 긴급 주목형(노랑·검정, 목격 장소 강조)으로 문구·배치·색상을 구분했다. 서버 프리셋에 필수 텍스트 8종을 모두 배치하고 프론트의 공통 좌표 덮어쓰기를 제거했다. 한글 고딕 폰트 스택과 기본 행간 1.3을 렌더링·넘침 측정에 함께 적용했다. 기존 저장 문서는 자동 재배치하지 않으며 새 템플릿 선택 시 적용한다.

검증: 전단지 백엔드 테스트 6개 통과(모의 환경), 프론트 테스트 파일 12개 통과, Vite production 빌드·Ruff·공백 검사 통과. 좌표·필수 필드·컴포넌트 간 겹침과 템플릿 전환 시 문구·사진 보존을 검증했다. 제한 환경에서는 TestClient 스레드 통신이 멈춰 동일 백엔드 테스트를 제한 밖에서 실행했다. 브라우저 시각 검수·실물 출력·기기별 폰트 비교·배포는 수행하지 않았다.

### board-breed-v1 / feature-extract-v6 (2026-11-17)

게시판의 [이 정보로 구조 공고 찾기]가 품종을 특징란에 붙이고 품종 선택값을 비우던 오류를 수정했다. 회원 글 등록을 공식 품종 셀렉트로 바꾸고 서버에서 축종별 활성 코드를 검증해 breed_code와 공식 품종명을 저장한다. 기존 글·공공데이터 분실 신고는 조회 시 공식명·별칭의 유일한 일치로 코드를 제공한다. 모호하거나 없는 품종은 빈 코드로 두고 기준정보 조회 실패는 오류로 구분한다. 검색 화면에는 코드를 그대로 전달하며 품종을 특징 문구에 추가하지 않는다. 글 특징 추출 프롬프트에 품종명·코드를 marks에서 제외하는 지침을 추가하고 프롬프트 버전과 모델 캐시 키를 v6로 올렸다.

최종 검증: main 기준 독립 브랜치에서 백엔드 전체 229개, 프론트 테스트 파일 9개, Vite production 빌드·Ruff·공백 검사 통과. 모의 기준정보로 코드 저장·공식명 보정·다른 축종/미등록 코드 거부·기존 글·분실 신고·별칭·모호한 이름·조회 실패 및 검색 미리 채우기를 검증했다. 외부 API 실제 호출·실제 LLM 판단·브라우저 시각 검수·배포는 수행하지 않았다.
